# 匹配页按主食材分组推荐设计

## 目标

- 让用户选择 `鲈鱼 / 豆腐 / 鸡蛋 / 鸡肉` 等主食材后，能即时看到与该主食材强关联的菜谱。
- 避免匹配页一次性铺太多菜，减少长列表滚动负担。
- 让推荐结果具备更强的决策感，区分“现在就能做”和“差一点就能做”。

## 当前问题

- 现有匹配页虽然已经加入主食材强关联排序和推荐 5 道，但仍然是单流式结果。
- 当用户选中多个主食材时，所有菜仍然混在一个推荐区里，不利于快速理解“哪个菜是围绕哪个主食材推荐的”。
- 用户需要更直观地看到“鲈鱼可以怎么做”“豆腐可以怎么做”，而不是反复切换焦点或展开更多内容。

## 设计方案

### 展示结构

- 匹配页改为“按主食材分组推荐”。
- 每个主食材生成一个独立分组，例如：
  - `鲈鱼可以这样做`
  - `豆腐可以这样做`
  - `鸡蛋可以这样做`
- 每组最多展示 3 道菜，结构固定为：
  - `可直接开做`：最多 2 道
  - `差一点就能做`：最多 1 道

### 组内规则

- 同一道菜若命中多个主食材，只归到“最强关联”的一个主食材分组，避免重复出现。
- 若某个主食材不足 3 道菜，则按实际数量展示，不强行补满。
- 若某组没有“差一点”菜，则只显示“可直接开做”。
- 若某组没有“可直接开做”，则可只显示“差一点就能做”。

### 主食材定义

- 继续沿用当前匹配逻辑中的主食材判定：
  - 允许作为主食材分组：`seafood / meat / tofu / egg / veg / staple / fruit`
  - 不作为主食材分组：葱、姜、蒜、香菜、辣椒等辅料

### 排序规则

- 分组顺序按主食材优先级排列：
  - 海鲜
  - 肉禽
  - 豆腐
  - 蛋类
  - 蔬菜
  - 主食
  - 水果
- 组内菜谱优先级：
  - `可直接开做` 优先于 `差一点`
  - 主食材命中数高优先
  - 总缺失更少优先

## 页面呈现

### 页面上半区

- 保留“已选食材”概览卡片。
- 将原本的“主食材切换 chip + 推荐 5 道”替换为“主食材分组推荐区”。

### 每个分组卡片

- 标题：`鲈鱼可以这样做`
- 副标题：`优先给你 2 道可直接开做，再补 1 道差一点就能做`
- 内容区分两块：
  - `可直接开做`
  - `差一点就能做`

### 菜谱卡片

- 保持现有卡片风格，不做大改。
- 继续显示：
  - 菜名
  - 分类 / 时间 / 难度
  - 已命中
  - 还缺
  - 加入订单
- 强化一行说明：
  - `主食材命中：鲈鱼`

## 数据与实现

- 在 `utils/match.js` 中新增按主食材分组的结果结构。
- 输出形态建议为：
  - `focusId`
  - `focusTitle`
  - `readyRecipes`
  - `almostRecipes`
  - `summaryText`
- 在 `pages/match/index.js` 中将当前 `recommendedRecipes / moreRecipes` 改为 `recipeGroups`。
- 在 `pages/match/index.wxml` 中按 group 渲染独立 section。

## 边界处理

- 若用户没有选择任何主食材，则保持空状态提示。
- 若只有一个主食材，则只展示一个分组。
- 若用户选择很多主食材，允许页面出现多个分组，但每组最多 3 道，整体仍可控。
- 若某一道菜同时命中多个主食材，必须只出现一次，避免重复推荐。

## 测试策略

- 增加匹配分组脚本测试，覆盖：
  - 选择 `鲈鱼` 时出现鲈鱼分组
  - 鲈鱼分组中 `清蒸鲈鱼` 优先进入 `可直接开做`
  - 每组最多 `2 道可直接开做 + 1 道差一点`
  - 同一道菜不会重复出现在多个主食材分组中
- 更新匹配页模板测试，断言页面已切换到 `recipeGroups` 结构。
